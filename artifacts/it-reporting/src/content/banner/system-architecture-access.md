# Student Identity, Provisioning, and Enrollment Architecture

**Document owner:** Information Technology
**Environment:** SCCC Production
**Last reviewed:** August 20, 2026

## Purpose and scope

This handbook describes the complete student identity path from an accepted Banner admission through AD, Microsoft Entra, Google Workspace, Banner write-back, Canvas, operational reporting, and recovery. It identifies what each system owns, where each component runs, how it is accessed, and which controls prevent one person from being confused with another.

## Non-negotiable identity rules

1. **Names are not identity keys.** A person is resolved by the Banner 800 number, Banner/Ethos person UUID, EID/UDC, and the immutable object ID of the destination system.
2. **A student must be eligible in Banner.** An existing AD, Entra, Google, or Canvas account never proves current admission or enrollment.
3. **Staff are excluded before student actions.** An exact AD/Entra identity outside `OU=StudentPopulation,OU=People,DC=sccc,DC=edu` cannot receive a student Google account, student license, or student write-back.
4. **One defect cannot block the queue.** Ambiguous or invalid identities are held individually and reported while other eligible students continue.
5. **No name-only adoption.** An untagged Google user, an alias, or a similarly named directory object is never assumed to be the student.
6. **No bulk user changes without approval.** Read-only bulk verification is permitted; bulk modifications require an explicit, scoped authorization and a rollback plan.

## End-to-end operating flow

The canonical Canvas identity chain is exact and one-way: **EUP `xEup.collegeEmail` → sole active/preferred GOAEMAL `STD` address → its collision-checked local part in GOATPAD Third Party ID → on-premises AD `mailNickname` → Entra Cloud Sync Alias → Entra `user.mailnickname` SAML `NameID` → Canvas login `unique_id`**. Each hop must preserve the same value. GOATPAD, AD, Entra, and Canvas consume the EUP identity; none may create a separate first-initial username.

1. Admissions completes the application and an accepted current-term decision in Banner.
2. Ethos exposes the person, application, decision, academic period, and EUP identity profile.
3. Ellucian EUP/AgentAD is the primary AD creation path. The independent monitor watches every two minutes and gives EUP a ten-minute grace period.
4. If the exact AD identity is still missing after the grace period, the guarded Windows recovery task may create **one missing user** only after unique 800, EID, username, and CN checks.
5. The prepared guarded post-create policy resolves the live Banner `bannerUserName` by exact 800 number, person UUID, and EID/UDC, then ensures AD `mailNickname` contains that value. Its ENTRACLOUDCON script/task replacement is **pending the corporate VPN/admin channel** and is not yet active; until deployment, the report detects alias mismatches but current recovery does not promise automatic `mailNickname` enforcement. A missing, duplicate, or conflicting credential must always be quarantined rather than guessed.
6. AD Cloud Sync produces the same immutable identity in Entra and maps AD `mailNickname` to Entra Alias. The worker's delta index must find exactly one enabled StudentPopulation object.
7. The static `LIC-O365-A1-STUDENTS-NO-EXCHANGE` group assigns A1 Student and disables Exchange Online. The current automated membership publisher still requires ownership verification; the worker/report must verify the resulting membership and license rather than claim an unproven assignment path.
8. Google provisioning proceeds only after Entra validation and exact Google address/marker ownership checks.
9. The guarded GOAEMAL writer uses the supported API and reads back every write. The routine GOATPAD Third Party job is strictly read-only: it verifies the exact live Banner/Ethos `bannerUserName` and never derives or writes a credential.
10. The protected EUP report merges current verification snapshots, including the Entra `mailNickname` versus Banner/Canvas login check; it is an operational view, not a source of truth.
11. Account completion may request an ACR registration refresh. Only official Banner section registrations affect ACR headcount and credit hours. Canvas course membership must also originate from official registration, but the current publisher/owner/schedule of the Banner-to-Canvas enrollment integration still requires verification.

## Known access-hardening work

These items do not invalidate the identity workflow, but they should be tracked as security/continuity improvements:

1. **Canvas integration identity:** the ACR Canvas API token is currently owned by a named human Canvas account. Replace it with a dedicated, least-privilege integration identity, rotate the token, and verify the ACR sync before revoking the human-linked credential.
2. **Windows task self-modification:** the `ENTRACLOUDCON` monitor directory currently grants the reconciliation managed service identity inherited Modify rights over its scripts and signing key. Separate code/config write ownership from task execution, retain only the minimum read/execute and required state-write permissions, then verify all three scheduled tasks.
3. **Off-host recovery:** `/var/backups/sccc-acr-recovery` is empty and the required `age` recipient configuration is not installed. Configure an approved public recipient, off-host destination, retention policy, and a tested restore before claiming host-loss protection.
4. **Machine-only ACR refresh route:** EUP correctly calls the registration-refresh API over `127.0.0.1`, and external unauthenticated access is rejected with `401`. Add an exact Nginx deny for the machine-only path so it cannot be reached from the public proxy at all.
5. **Cloud Sync maintenance:** the agent has live relay connections and downstream synchronization proof, but its local trace file can remain old. Health must combine service state, relay sessions, and downstream evidence rather than treating trace age alone as a stopped sync; upgrade the agent during a controlled maintenance window.
6. **Linux service separation:** the Hub API, ACR, stand-alone report, and IT portal mostly share the `scccadmin` OS identity. The EUP state directory is `root:scccadmin` mode `2770`, so that identity can read required snapshots but also has directory-level replace/delete capability. Move consumers to separate service identities and expose verified snapshots through a read-only group or API boundary.
7. **SSH exposure:** the current Azure network rule permits key-based TCP 22 access to `app-server2` from the Internet. Restrict approved source networks or use Azure Bastion/Just-in-Time access, then verify emergency access before removing the broad rule.
8. **Canvas enrollment integration ownership:** Canvas has current student users and enrollments, but the latest visible native SIS-import history does not prove a contemporary publisher, and ACR only reads Canvas. Identify the actual Banner/Ellucian/API publisher, service identity, schedule, retry behavior, and alert owner before claiming an end-to-end Canvas enrollment SLA.
9. **Student-license membership ownership:** the static no-Exchange group and its resulting license are verified, but the current automated process that adds each new student to that group has not been identified in the worker configuration/logs. Establish the authoritative membership publisher, service identity, retry/alert behavior, and an exact read-back test.

## Failure isolation and alerting

| Checkpoint | Fail-closed condition | System response |
|---|---|---|
| Banner person | Zero or multiple persons for one 800 number | Hold the record; do not infer by name |
| Eligibility | No accepted decision for a configured current term | Exclude from provisioning |
| AD | Duplicate 800/EID, username/CN collision, disagreement between `description` and `extensionAttribute2` | Quarantine one student; continue the queue |
| Staff boundary | Matching identity is outside StudentPopulation | Record staff exclusion and block all student actions |
| Entra | Disabled/missing object, duplicate immutable match, EID/800 mismatch, or stale sync | Wait or quarantine; no Google action |
| Google | Address is an alias, account is untagged, marker belongs elsewhere, or multiple marker owners exist | Quarantine; do not adopt, rename, or create |
| GOAEMAL | Canonical row missing/inactive, multiple preferred rows, or API verification unavailable | Add/repair only through the guarded reconciler; distinguish API outage from student defect |
| GOATPAD | The exact live Banner/Ethos `bannerUserName` is missing, duplicated, or disagrees with immutable person evidence | Block and report; never synthesize a credential or change PIN data |
| Canvas | Multiple users/logins or immutable IDs disagree | Block exact correction; preserve enrollments |
| Recovery | Any source is stale, partial, or inconsistent | Preserve the prior last-good snapshot and record a failed attempt |

The health monitor applies a real grace period to normal in-progress states, suppresses repeated duplicate alerts, and sends incident/recovery notifications to the configured IT recipients. A stale worker, Cloud Sync heartbeat, verifier, or recovery job is an infrastructure incident—not a student-account defect.

The Production alert path is also guarded: `/opt/sccc-eup-health/eup-health-monitor.py` reads the current EUP state files, persists de-duplication state, signs its loopback request with the restricted monitor key, and posts to `127.0.0.1:8080/api/internal/eup-alert`. `ENTRACLOUDCON` sends its signed snapshot and heartbeat to the private `app-server2` address. The Hub API validates the signature, private source, and timestamp before sending Microsoft 365 SMTP notifications to the configured IT distribution mailbox and designated incident owner; Nginx returns `404` for public `/api/internal/` requests. Normal student stages receive a 15-minute grace, stale core worker/heartbeat evidence alerts in roughly 6–10 minutes, and unchanged incidents are repeated no more often than the configured six-hour interval.

## Recovery and continuity

- The ACR ledger stores sanitized, append-only snapshots with per-record hashes and a manifest hash.
- Recovery records include the institutional and immutable identifiers needed to re-establish relationships; they exclude passwords, tokens, and private keys.
- A snapshot is evidence, not permission to replay changes. Restoration begins with a read-only comparison and requires approval for any write set.
- The prior last-good snapshot remains current if a collection is incomplete.
- The current automatic snapshot provides up to roughly a 24-hour recovery point. Encrypted off-host export should be enabled and tested before claiming protection from loss of the `app-server2` host itself.

## Controlled correction procedure

1. Freeze the exact Banner ID, EID, person UUID, destination immutable object ID, and current values in an audit record.
2. Query every affected system by durable/immutable identifiers and prove there is exactly one owner.
3. Classify the issue as source data, eligibility, provisioning, synchronization, write-back, downstream display, or reporting-only.
4. Let the normal automation finish when the state is inside its documented grace period.
5. For an existing user or any bulk write, obtain explicit scoped approval. A read-only bulk check does not require bulk-write approval.
6. Change the smallest possible field on the exact immutable object. Preserve unrelated attributes, groups, licenses, channels, and enrollments.
7. Read back the source and destination immediately. If verification fails, roll back or quarantine; never assume success from an HTTP status alone.
8. Allow the next sync/reconciliation cycle to update the protected report, then capture recovery evidence.

## Reporting contract

The stand-alone EUP report and the IT Hub are operational projections. A row is green only when the currently applicable checks have read-back evidence. Historical activity remains audit history and must not be presented as a current unresolved error after the inventory is verified. API outages and stale snapshots must be labeled **verification unavailable**, not counted as broken student accounts.

The authoritative sequence remains:

**Banner eligibility → EUP/AD → Entra/Cloud Sync → A1 Student without Exchange → Google → Banner GOAEMAL/GOATPAD read-back → protected reporting.**

Official enrollment is a separate sequence:

**Banner section registration → ACR enrollment refresh and the separately owned Canvas enrollment integration (publisher and schedule still to be verified).**
